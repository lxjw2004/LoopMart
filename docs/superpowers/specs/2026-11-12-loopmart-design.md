LoopMart 面向 bm 当前服务的校园／社区，提供二手市场、拼车、发布、收藏、个人中心和站内私聊。首版交付响应式用户 Web 和 Admin，iOS 后续开发。

本次已检查 bm 的 PRD、商品与拼车模型、认证逻辑相关代码、Admin 页面目录、Admin README 与依赖。参考目录主要包含 iOS 用户端和 Next.js Admin，未发现独立用户 Web。源目录根不是 Git 仓库，尚未核实各子项目提交历史。本次不是逐行完整审计，不能声称已穷尽所有行为。

功能判定顺序：用户在本次对话中的明确决定优先；其次是 bm 实际有效业务行为；PRD 作为补充。旧文档、旧界面和实际后端规则不一致时，实施前记录差异并确认，不直接复制缺陷。

“与 bm 一致”指适用功能与业务规则对齐，不要求复制 iOS 专属交互、Supabase 实现或原有缺陷。原项目仅只读参考，不修改。

## 3. 服务器与目录安排

只读检查发现 OCI 为 Ubuntu 24.04、ARM64、4 核、24 GiB 内存；检查时可用内存约 17 GiB，`/data` 可用约 66 GiB。数据会变化，不作为容量承诺。服务器已有 Docker、1Panel、OpenResty 和多个 PostgreSQL 服务。

现有 Cardmaster 认证项目位于 `/data/better-auth/`，Compose 文件为 `/data/better-auth/compose.yaml`，源码构建目录为 `service/`，现有认证容器为 `better-auth-cardmaster-1`。Better Auth 库安装在该容器的 `/app/node_modules/better-auth/`。未读取密钥、环境变量或业务数据。

用户选择“统一目录管理多个独立认证服务”，但明确暂不整理 Cardmaster。LoopMart 认证拟放在 `/data/better-auth/loopmart/`。此路径仅为设计，尚未创建。

未来部署应遵守：

- LoopMart 使用独立 Compose 项目名、数据库用户、数据库、网络、端口、Cookie 和认证密钥。
- 不修改 Cardmaster 现有文件、容器、数据库或密钥。
- 不在父目录执行可能作用于 Cardmaster 的 Compose 命令；操作时显式指定 LoopMart 文件及项目名。
- 部署前核查现有 Compose 是否使用递归绑定目录或相对路径，确保新增子目录不会进入 Cardmaster 构建和挂载范围。
- 项目源代码统一维护；服务器认证目录只管理 LoopMart 认证部署材料，避免复制出两套不可追踪源码。
- Web／Admin／API 的服务器目录可建议使用 `/data/loopmart/`，但尚未批准具体部署布局。

选择独立 PostgreSQL 容器还是复用现有实例中的独立数据库，留到部署设计审核。推荐独立容器以便生命周期隔离，但不因此启动任何服务。两种方案都必须隔离数据库账号，不允许访问 Cardmaster 数据。

## 4. 架构方案比较

### 4.1 方案一：单仓库、模块化后端与独立认证进程（推荐）

同一仓库维护 Web、Admin、业务 API 和认证服务，共享契约、校验和国际化资源。认证为独立部署单元，满足 `/data/better-auth/loopmart/` 的安排。业务 API 承担访问控制、数据库读写和实时聊天。

优点：边界清楚，容易测试和维护；iOS 后续复用 API；既能统一开发又能独立部署认证。代价：需明确跨进程会话验证、代理路由及失败处理。

### 4.2 方案二：Next.js 全栈集中实现

Web、Admin、认证和业务请求主要集中于同一应用，实时连接另设服务或受控自定义服务。

优点：初期部署单元少，接近 bm Admin 技术栈。代价：难以同时维持独立认证部署边界；聊天长连接与页面服务生命周期耦合，后续 iOS API 容易散落。

### 4.3 方案三：按业务拆分微服务

认证、市场、拼车、聊天、管理分别独立服务。

优点：可独立扩容与发布。代价：跨服务一致性、可观测性、网络与运维成本较高；当前单社区规模缺少足够收益。

建议采用方案一。该推荐尚需用户批准，不是已经选定的最终技术方案。

## 5. 建议技术组成与模块边界

建议使用 TypeScript 单仓库；Web 和 Admin 使用 Next.js／React，沿用 bm Admin 已有技术经验；API 与认证使用 Node.js，数据库为 PostgreSQL。具体版本、ORM、实时库和构建工具在实施计划中核对官方兼容性后锁定，不在本稿中虚构版本兼容结论。

建议仓库结构：

```text
apps/
  web/                用户 Web
  admin/              管理后台
  api/                业务 API 与实时连接
  auth/               LoopMart 独立 Better Auth 服务
packages/
  contracts/          API 契约、错误码、运行时校验
  database/           业务数据库模型与迁移
  ui/                 共享基础组件与设计变量
  i18n/               中英文资源
  integrations/       邮件、媒体适配边界
infra/                待批准的部署模板
docs/                 设计、核对清单与验收记录
```

业务模块包括身份接入、社区与资料、商品、拼车、收藏、聊天、举报、社区管理员消息、联系表单、运行配置、审计。每个模块拥有自己的业务规则，通过明确接口访问其他模块，不让页面直接执行数据库操作。

认证服务负责账号、密码、验证令牌、会话。业务 API 根据服务端可信会话识别用户，再查询社区资格和角色。客户端传来的用户 ID、角色或“已验证”标记不能作为授权依据。会话检查优先通过认证服务的受保护内部接口完成；失效时拒绝受保护请求，不静默放行。具体会话检查实现须结合选定 Better Auth 版本验证。

## 6. 用户 Web 功能设计

### 6.1 导航与响应式

保留二手、拼车、发布、消息、个人这五类入口。手机采用适合触屏的导航，桌面使用清晰的页头导航、内容宽度和双栏聊天布局。保持 bm 色彩、字体层级、圆角和间距方向，具体值需从原设计代码核对后整理。

首版不使用空白大图模拟商品照片，采用文字卡片突出标题、价格、分类和发布者。移动端与桌面使用同一业务能力，不把 iOS 屏幕直接放大为桌面页面。

内部设计原则不转成页面宣传文案。尽量避免冗余副标题、口号、解释段落；必要补充信息使用精简提示或可访问的 tooltip。正常状态、空列表、加载、权限不足、失败、已下架状态均有明确且简短的反馈。

### 6.2 账号与个人资料

邮箱＋密码注册与登录；注册资格由服务端执行邮箱后缀规则。后缀按域名边界匹配并统一大小写，不能用任意字符串包含判断。邮箱验证和密码找回链接使用可信回跳地址和有时效的令牌。

SMTP 主机、端口、用户名、密码、发件人配置留空；仅预留服务端配置。无真实邮件服务时，不伪装发送成功、不自动验证账号、不记录可用验证链接到生产日志。密码找回对外使用一致反馈以避免泄露账号存在性；发信不可用通过服务状态和受控运维日志识别。验证重发等已知登录状态操作可明确反馈邮件服务不可用。测试流程使用隔离的模拟发信适配器，不改变生产授权规则。

个人中心包括昵称编辑、默认头像、我的商品、我的拼车、商品收藏和账号操作。公开主页仅返回公开资料和可公开的发布内容，不向游客暴露完整邮箱。修改邮箱及注销账号是否属于必须保留的 bm 有效行为，需要实施前核对有效调用链，不推断数据删除策略。

### 6.3 二手市场

浏览商品列表和详情；按名称搜索、按分类筛选，分页加载。商品字段参考 bm：标题、描述、分类、价格、成色、交易地点／方式、发布者和状态。

默认分类沿用衣服、书、家具、电子产品、生活用品、其他；分类和成色使用稳定代码，中英文标签在展示层映射。价格默认美元，仅展示，数据库使用精确数值或最小货币单位，避免浮点累计误差。

支持发布、编辑、下架、收藏／取消收藏、联系卖家及公开资料入口。发布者只能管理自己的内容；管理员的操作走独立受审计接口。首版不接收媒体或外部图片 URL。交易方式与地点在 bm 模型和 PRD 表述有差异，具体字段需核对有效发布与管理表单后冻结。

### 6.4 拼车

提供列表、详情、出发地／目的地／日期筛选与出发时间排序，支持预设地点及自定义地点。字段包括路线、出发时间、IANA 时区、总座位、可用座位、每人费用、费用说明和备注。

时间以 UTC 时间点加原始时区存储；日期筛选按明确定义的出发地时区换算，不直接使用服务器日期。校验可用座位不超过总座位、费用非负、时区有效。座位为发布者维护的信息，不生成支付订单、不自动扣减、不构建订座事务。

支持发布、编辑、下架及联系车主。拼车收藏在当前已查看的 PRD 中不是明确功能，首版收藏基准为商品；若 bm 有有效实现，再补齐核对清单。

### 6.5 草稿与联系表单

bm 源码存在发布草稿管理及联系表单相关模块。建议保留发布草稿恢复和“联系我们”提交能力；草稿是否跨设备、退出时是否保留须按原实现核对，不能把本地草稿擅自扩为云端同步。

联系表单由后台管理，用户提交与通知发送解耦；SMTP 暂未配置时仍可保存表单，不声称已发邮件通知。可配置的外部通知渠道只预留边界，不默认引入飞书或其他外部服务。

## 7. 实时聊天设计

### 7.1 功能与授权

支持文字私聊、会话列表、最后消息摘要、未读数量、已读状态，以及商品／拼车上下文引用。每条消息及历史查询均校验参与者资格；管理员会话查看通过明确管理权限，不复用普通用户接口绕过限制。

会话唯一性已由用户明确：按用户对合并，不按商品或拼车分会话。无论采用哪种规则，都用数据库唯一约束避免并发创建重复会话，不能仅靠前端检查。

### 7.2 发送、重连与已读

建议浏览器通过 WebSocket 接收实时事件，消息提交使用可幂等的服务端写入接口。先提交数据库，再通知接收方；客户端不能将“已进入发送队列”显示成“对方已读”。

客户端为发送生成幂等标识；服务端以发送者和标识唯一约束防止重试重复。断线重连通过服务端消息序号或游标补齐历史，不依赖实时事件保证最终完整性。服务端保存每个参与者单调递增的已读位置，未读数由服务端规则统一计算，多设备状态可同步。

聊天引用保存必要的展示快照与目标 ID；原内容下架或删除后，历史对话仍有可理解上下文，跳转时遵守目标当前可见性。

首版单 API 实例即可，不强制引入 Redis。多实例扩容时再引入跨进程事件分发；届时需另行设计可靠投递及运维，不提前引入基础设施。

## 8. Admin 功能范围

| 模块 | 首版能力 |
|---|---|
| 概览 | 沿用 bm 实际统计口径，展示用户、商品、拼车及待处理信息 |
| 用户 | 列表、详情、创建、资料管理、角色管理、封禁，以及适用的密码管理 |
| 商品 | 列表、详情、创建、修改、审核／强制下架或删除 |
| 拼车 | 列表、详情、创建、修改、强制下架或删除 |
| 举报 | 查看目标与原因、审核处理、记录结论和备注 |
| 会话 | 受控查询会话与消息，避免无权限数据泄露 |
| 社区管理员 | 配置管理员身份、管理管理员会话、发送管理消息 |
| 审计 | 查询敏感操作主体、对象、理由、前后变更与时间 |
| 认证设置 | 允许全部域名或邮箱后缀白名单 |
| 联系表单 | 查看提交、处理状态及适用通知配置 |
| 隐私政策 | 中英文内容管理与用户端展示 |
| 媒体、iOS 启动页 | 首版暂缓，不展示无效上传或 iOS 配置入口 |

后台创建账号、发送密码重置、设置密码等能力须结合 bm 实际实现保留，并通过 Better Auth 受控接口执行，不直接写密码字段或擅自复制 Supabase Auth 表结构。邮件重置在 SMTP 配置前不可真正送达。

敏感操作要求理由、适当二次确认和服务端授权。角色调整、封禁、强制删除、敏感配置及密码管理记录审计，但审计不得保存密码、令牌和 SMTP 凭据。管理员设置密码不应回显既有密码。

举报结果与社区管理员消息采用数据库事务或持久化待发送记录避免“审核完成但通知永久丢失”；消息通知失败不撤销审核结果，后台可识别并重试。具体通知文案和触发条件按 bm 有效流程核对，不增加营销消息。

## 9. 建议数据设计

下表是逻辑实体，不是已经批准的 SQL schema。

| 实体 | 核心职责与约束 |
|---|---|
| Better Auth 表 | 用户、会话、账号、验证；遵守库的模型与迁移约定 |
| profiles | 昵称、语言、默认头像信息；关联认证用户 |
| communities | 首版唯一默认社区，稳定 ID |
| memberships | 用户与社区、角色、封禁状态；唯一社区成员关系 |
| items | 商品业务字段、社区、发布者、状态、版本和时间 |
| rides | 路线、时区、座位、费用、社区、发布者和状态 |
| favorites | 用户与商品唯一关系，防止重复收藏 |
| conversations | 社区、会话类型和受控上下文关联 |
| conversation_members | 参与者及已读位置 |
| messages | 会话、发送者、文字、引用、幂等标识与排序位置 |
| content_reports | 举报人、目标、原因、审核状态、处理人及备注 |
| contact_submissions | 联系表单及处理状态 |
| runtime_settings | 域名策略、隐私政策和社区管理员等非密钥配置 |
| audit_logs | 敏感操作审计，不包含凭据 |
| notification_jobs | 需要保证重试的后台通知任务 |

用户标识按 Better Auth 选定配置的实际类型统一，不能假设 bm UUID 能原样迁移。认证与业务使用逻辑分区或明确表归属，独立数据库账户按职责授权。

商品与拼车保留社区 ID；首版由服务端固定选择默认社区，客户端不能任意指定社区。会话与举报保持同社区关联约束。未来多社区需要补齐加入资格、账号归属、角色和跨社区可见性设计，预留字段不等于已实现多社区。

媒体暂以稳定的可空媒体引用契约预留，不创建无用对象存储、不启用签名上传 API。后续媒体服务负责对象标识、状态、大小／类型校验和可见性，不把任意外部 URL 当可信资产。

删除区分用户下架、审核隐藏和物理删除。与历史消息、举报、审计关联的数据优先保留必要引用，具体保留期限及账号删除政策需单独确认后落地。

## 10. API、权限与安全

建议 API 采用稳定版本前缀，按商品、拼车、收藏、资料、聊天、举报、联系表单、管理功能划分路由。公开查询仅返回有效可公开内容；管理查询使用独立权限入口。响应包含稳定错误码、必要错误字段和请求标识，中英文展示由前端资源控制。

权限层次为游客、已验证成员、内容所有者、管理员；封禁检查覆盖新请求和现有实时连接。前端隐藏按钮不构成授权。服务端需要检查登录、验证、社区资格、角色、对象归属、目标状态。

使用安全 Cookie 与受控 Origin，避免宽泛跨域和父域 Cookie。优先由反向代理为各客户端暴露受控认证路径，具体域名布局在部署前确认。修改状态的请求实施 CSRF／Origin 防护，WebSocket 握手也校验身份和来源。

注册、登录、重发、找回密码、发布、聊天和举报设置适当频率与体积限制。用户文本默认转义；隐私政策如使用富文本应净化。SQL 使用参数化查询。日志、错误响应、审计均不泄露数据库连接串、邮箱验证令牌或密码。

## 11. 媒体与邮件扩展接口

媒体适配器仅定义能力契约，例如申请上传、确认完成、获取可访问引用、删除；首版实现明确返回未启用，不连接 S3、CloudFront 或其他存储。前端不展示这些入口。

邮件适配器接受收件人、语言、模板类型与令牌链接，由 SMTP 实现负责投递。凭据只放服务端秘密配置，不写入代码、公开配置 API 或管理审计。首版空配置不阻止游客浏览，但无法完成真实邮件注册验证和找回密码，这属于明确交付限制。

Better Auth 的验证和找回流程支持注入发信函数；认证库与 SMTP 发信职责分离。参考官方文档：https://better-auth.com/docs/authentication/email-password 。本项目不接入 Better Auth 托管邮件服务。

## 12. 分阶段实施规划草案

本节是供审阅的阶段路线，不是实施授权。正式逐任务计划在本稿批准后形成，并核对工具链与接口细节。

### 阶段 0：功能基线与技术验证

补齐 bm 有效页面、API、SQL 和权限的对应清单；标记保留、替换、暂缓项。核实会话唯一性、消息功能、举报对象、草稿、用户账号管理、删除规则及交易方式字段。读取实际主题和本地化资源形成设计基准。验证所选 Better Auth、Node.js、数据库适配器及 ARM64 部署兼容性。

验收：每项适用 bm 功能都有目标模块和验收场景；冲突规则已解决；不再以“全部一致”代替具体清单。

### 阶段 1：基础架构、认证与权限

建立单仓库及共享契约，完成数据库迁移基础、默认社区、Better Auth、会话验证、角色和封禁规则、中英文骨架。SMTP 接口和配置留空，测试使用独立模拟适配器。制定首次管理员建立方式，不公开默认管理员密码。

验收：隔离环境覆盖注册资格、验证、登录、退出、找回流程和权限；空 SMTP 不绕过验证；不接触 Cardmaster。

### 阶段 2：市场、拼车与个人中心

完成响应式列表、详情、筛选、发布、编辑、下架、商品收藏、公开资料、我的发布及适用草稿能力。

验收：游客可读，未验证用户不能写；所有者检查有效；价格、座位、时区、分页及并发修改边界可复现验证；全流程中英文可用，无媒体入口。

### 阶段 3：聊天与社区通知

实现会话建立、文字消息、内容引用、实时连接、断线补齐、幂等发送、已读和未读；实现管理通知的持久化重试边界。

验收：双用户实时互发，多标签页已读同步，重复发送不重复落库，断线后不丢历史；非参与者无法订阅或读取会话；封禁和会话过期后不能继续发送。

### 阶段 4：Admin、举报与运行配置

补齐用户、商品、拼车、会话、举报、管理员消息、审计、联系表单、认证策略和隐私政策配置。复核 bm Admin 各页面功能，不遗漏适用操作。

验收：所有管理写入有服务端权限；敏感动作记录理由和审计；举报通知失败可重试；SMTP 留空的相关操作有明确可理解结果。

### 阶段 5：完整回归与部署准备

进行端到端功能、授权、响应式、中英文、数据一致性和聊天恢复测试。准备 ARM64 镜像方案、迁移／备份／恢复说明和独立 Compose 模板。核对目录、端口、反向代理、数据库和磁盘需求。

验收：本地或隔离测试环境可重建，部署变更可审查；没有已执行 OCI 部署。真实上线、数据库创建、域名／代理变更和 SMTP 接入需要后续明确授权。

## 13. 验证方案与验收矩阵

| 范围 | 必须覆盖的场景 |
|---|---|
| 认证 | 域名边界、大小写、重复注册、过期／重复令牌、错误密码、退出与会话失效 |
| SMTP 空配置 | 无假成功、无自动验证、无生产令牌泄露、找回响应不泄露账号 |
| 权限 | 游客读、验证后写、他人编辑拒绝、普通用户管理接口拒绝、封禁拒绝 |
| 商品 | 搜索筛选、分页、零价／非法价、收藏幂等、下架详情与引用处理 |
| 拼车 | 时区与夏令时、日期筛选、座位上限、非负费用、已下架状态 |
| 聊天 | 重复建会话、发送重试、消息顺序、重连补齐、已读单调、多设备未读 |
| 举报与后台 | 敏感操作、审计、目标失效、审核通知失败与重试 |
| 多社区预留 | 服务端固定社区、拒绝伪造社区参数、查询不漏过滤 |
| 用户体验 | 桌面／手机、键盘可达、加载／空态／错误、中英文无缺失键 |
| 隔离与部署 | 不引用 Cardmaster 凭据、端口不冲突、独立项目名和数据库权限 |

测试优先使用有意义的权限、事务、边界与端到端场景，不堆砌只镜像实现的测试。每阶段执行相关测试、类型检查和构建。测试未执行则明确标记，不将本设计中的验收要求写成已通过结果。

本轮实际验证仅包括本地源码只读检查及 OCI 系统、容器、路径的只读查询；尚无业务实现、测试通过或部署完成结论。
